== Cross-cutting Concepts

// Concerns that span building blocks and would otherwise be

=== Persistence

All data is in the filesystem: a user is a directory `data/<user>/`,
and a course is a directory in it holding the course PDFs and all
Markdown and JSON files, uploaded, derived, or written by the
tutor. There is no database.

Only open chats are stored: every topic keeps one `chat.json` with the transcript and token usage of their open session,
removed when the session ends. What lasts from a chat is in
`progress.json` and `cheatsheet.md`.

==== Storage Layout

Every course has one directory. Nothing outside `data/<user>/` belongs
to that user, and nothing inside it is read on behalf of another user.

....
data/<user>/<course>/
├── sources/
│   ├── exercises/          exercise sheets and solutions
│   └── exams/              past exams and solution proposals
│       ├── <file>.pdf      original
│       ├── <file>.md       conversion, one section per page
│       └── <file>/         figures of the conversion
├── notes.md                remarks on the course
├── cheatsheet.md           living artifact
├── topics.json             topic list
├── ingestion/              intermediate pipeline results
│   ├── topics.json         topics as extracted, and the files read
│   └── error.txt           why the last ingestion failed
└── topics/<topic>/
    ├── topic.md            topic artifact
    ├── solutions.md        reference solutions
    ├── progress.json       living artifact
    ├── usage.json          tokens of the topic's chats
    └── chat.json           open chat
....

The subdirectory of `sources/` is the document type, given by the
drop zone a PDF is uploaded in or the subdirectory the operator puts
it in (`exams/`, `exercises/`);
it is what the pipeline's source priority is applied to.

The files fall into three classes:

[cols="1,2,2", options="header"]
|===
| Class | Files | Written by

| Input
| `sources/*`, `notes.md`
| An upload in the UI or the operator's course command

| Derived
| `sources/*/<file>.md`, `sources/*/<file>/`, `topics.json`,
  `topic.md`, `solutions.md`, `ingestion/`
| Ingestion

| Student state
| `cheatsheet.md`, `progress.json`, `usage.json`, `chat.json`
| Chat tools for `cheatsheet.md` and `progress.json`, chats for
  `usage.json` and `chat.json`
|===

The student edits no file. Every Markdown file is shown rendered and
read-only in the UI, the conversions of the sources with their figures
in place. The source PDFs are shown with pdf.js in the browser.

Math in Markdown is written as `+\(...\)+` inline and as `+$$...$$+` or
`+\[...\]+` on lines of its own. The chat also renders inline
`+$...$+` as math when no space stands inside its delimiters; a `+$+`
next to a space is text, so amounts of money need no escaping. The prompts of every request whose output is
shown ask the model for this notation.

==== Cheatsheet Updates

`cheatsheet.md` is written only by the tutor, during any chat of the
course:

* The Course Store serializes writes per file.
* The cheatsheet is grouped in sections, one per topic (`##`), each
  holding entries (`###`). The tutor changes one entry - a heading and
  its body - in the current file, never the whole file.
* An open cheatsheet view reloads when the tutor changes it.

=== Source Conversion

Ingestion converts every source PDF with the Mistral OCR API (see
<<adr-mistral-ocr>>) into `sources/<type>/<file>.md`:

* Every page starts with `<!-- page <n> -->`, `<n>` counting from 1.
* A figure the OCR cuts out is a JPEG in `sources/<type>/<file>/`,
  named `p<n>-img-<i>.jpeg`, and referenced where it stands:
  `![p<n>-img-<i>.jpeg](<file>/p<n>-img-<i>.jpeg)`.
* Inline math `$...$` is rewritten to `+\(...\)+` outside of code;
  block math stays `+$$...$$+`.

The Markdown file is written last, so a source with a Markdown file is
converted completely; a resumed ingestion converts only the others.
A conversion is never changed afterwards.

A conversion consists of *blocks*: its paragraphs, split at blank
lines outside code blocks and `+$$+` math blocks, and every page
marker as a block of its own. Blocks are numbered from 1 per file.
Topic extraction and the tutor split a conversion the same way.

=== Topic Extraction

During ingestion the topics are data, not Markdown. Ingestion renders
`topic.md` from them.

* Extraction reads the course by unit (see <<adr-units>>): the files
  of one exam or one exercise sheet carry the same number in their
  names (`uebung01.md`, `loesung01.md`) and form one unit. A request
  carries the unit's conversions
  (<<_source_conversion,Source Conversion>>), each titled with its
  path below `sources/`, every block preceded by its number (`[12]`)
  and every figure replaced by `[figure]`, and the topics so far, each
  with its slug, name, description, and task labels.
* *Topic extraction* reads the past exams one after another, in the
  order of their numbers, with `notes.md`. The reply holds the
  language, the topics the exam creates or whose name or description
  it changes, and the exam's sources, each with the slug of its topic.
  A topic has a slug, a name, a description, whether the notes raise
  it, and its sources. The slug is its directory name.
* *Task assignment* then reads all exercise sheets at once, a few
  requests in parallel. The reply holds only the sheet's sources,
  each assigned to a topic with its fit - `clear` if it practises the
  topic's skill, `loose` if it only possibly belongs to it - or to
  `other-tasks`, a topic ingestion creates for the tasks no topic
  relates to. `topic.md` marks a loose fit, and the tutor uses such
  a task only where it serves the topic.
* *Task grouping* finally reads the tasks of `other-tasks` and, in a
  course with past exams, those of the topics no past exam asks for -
  numbered, each with its topic and blocks - and the topics. The
  reply holds new topics for tasks of `other-tasks` that practise the
  same skill, and every task that moves with its new topic and fit; a
  task of a topic no past exam asks for moves only when it clearly
  practises the skill of another topic. Tasks that fit nowhere stay;
  a topic of these tasks left empty is removed. The new topics have
  no past exam and so priority `low`. Without past exams, the
  exercise sheets go through topic extraction instead.
* Ingestion checks every reply - valid, unique slugs, a source for
  every new topic the notes do not raise, known topics and files, and
  blocks within each file - and repeats the request with the errors
  on a violation. It applies the replies in unit order and writes the
  topics and the files read so far to `ingestion/topics.json`: after
  every exam, once after all exercise sheets, including those of a
  failed ingestion that succeeded, and after the grouping, with the
  topic slugs and the tasks the grouping could move. A later
  ingestion reads only the units not read, and groups again only if
  those differ.
* A unit with a document not read yet whose other documents were read
  - solutions added to an exam, say - is read again: its earlier
  sources and the topics only they made up are removed first, so its
  tasks are not duplicated.
* The priority counts exams, not points, and is computed after the
  last unit: `high` if at least three quarters of the past exams have
  a source in the topic, `medium` if one does, `low` if none does.
  Without past exams, all units take their place. A topic the notes
  raise is `high`. `topic.md` names the number of past exams.
* A source is one task: its label (`Aufgabe 3c-e`), its gradability
  tier, and its block ranges, each in one file (see
  <<adr-task-blocks>>). The ranges cover the task, for a subtask the
  task's introduction, the figures, tables, and data it refers to,
  and its solution.
* `topics.json` stores every source with an ID, `<slug>/<n>`, and
  every block range with the pages it spans, read from the page
  markers; `topic.md` names these pages.
* For a topic chat, the Tutor loads every source of the topic
  in a `<source>` element with its ID, label, and tier, and in it
  every block range in a `<passage>` element with its PDF and pages.
  Figures in the blocks go as images where they stand, each after its
  Markdown image line with the path from the course directory. The
  topic's `solutions.md` follows in a `<solutions>` element.
* A task the tutor poses from the sources shows the figures of its
  statement: the tutor copies their image lines into the reply, and
  the chat resolves them against the course's files.
* The tutor links a task it poses from the sources, and a solution it
  shows from them, to the first PDF page of the passage, as a relative
  link with `#page=N`. The chat opens such a link in a tab beside
  the chat instead of following it.

=== Reference Solutions

The last step of ingestion writes a reference solution for every
Tier A or B task whose blocks hold no solution (see
<<adr-reference-solutions>>).

* One request per topic sends its sources exactly as a topic chat
  gets them, figures included, with its `topic.md` and the
  course language. The model finds the tasks without a solution
  itself and returns a solution for each with its task label, in the
  method, notation, and solution style of the topic's solved tasks,
  and whether it rests on values read from a figure.
* Ingestion checks that every label names a Tier A or B task of the
  topic, once, and repeats the request with the errors otherwise. It
  writes `topics/<topic>/solutions.md` - each solution under its task
  label, below a line saying the AI wrote them, not the course; a
  solution resting on values read from a figure is marked as such -
  and records in `ingestion/topics.json` a signature of the topic's
  tasks: labels, tiers, and blocks. A topic whose tasks all have
  solutions gets no file, or loses it. A later ingestion writes the
  solutions of a topic again whenever its tasks differ from the
  signature - new tasks, moved tasks, or a task that got solution
  blocks.
* The tutor grades such a task against its reference solution and
  tells the student once that the AI wrote it. When the student's
  answer differs, it checks both, since the reference can be wrong.
  When it poses a task whose reference is marked as resting on values
  from a figure, it tells the student to read the values carefully,
  and it does not count values that differ from the reference as
  wrong.

=== Security

==== Users and Courses

The operator manages users with the command line of the application
image; the UI has no login, no registration, and no account
settings. Courses are created, extended, and deleted by their user in
the UI, or by the operator from the command line.

....
docker compose exec backend iknownothing user add <name>
docker compose exec backend iknownothing user remove <name>
....

Adding a user creates their directory `data/<user>/`; removing a user
deletes it with all their courses.

....
docker compose exec backend iknownothing course add <user> <course> [<dir>]
docker compose exec backend iknownothing course update <user> <course> [<dir>]
docker compose exec backend iknownothing course ingest <user> <course>
docker compose exec backend iknownothing course remove <user> <course>
....

* `add` copies `notes.md`, `exams/*.pdf`, and `exercises/*.pdf` from
  `courses/<dir>/` (`<dir>` defaults to the course name) into the
  user's course and ingests it (<<runtime-ingestion>>).
* `update` copies `notes.md` and the PDFs of `courses/<dir>/` that an
  ingested course does not have yet, refuses a PDF whose content
  differs from the course's copy, and ingests what is new
  (<<runtime-ingestion>>).
* `ingest` runs the ingestion steps whose results are missing, e.g.
  after a failure.
* `remove` deletes the course with the student's state.

The HTTP API for courses, served for the user of the request:

* `GET /api/courses` lists the user's courses, each with its status
  (ready or not ingested), the step of a running ingestion, and why
  the last ingestion failed.
* `POST /api/courses` creates a course from a multipart upload of its
  name, notes, and the PDFs of past exams and exercise sheets, and
  starts its ingestion. A course name has lowercase letters, digits,
  hyphens, and underscores.
* `POST /api/courses/<course>/files` adds the uploaded PDFs the course
  does not have yet, replaces its notes, and starts the ingestion. A
  PDF whose content differs from the course's copy of the same name
  is refused.
* `POST /api/courses/<course>/ingestion` starts the ingestion again.
* `DELETE /api/courses/<course>` deletes the course with everything
  in it.

Adding files, starting an ingestion, and deleting are refused while
the course is being ingested. The mock user's sample course cannot be
changed.

The frontend lists all users; the student picks themselves, and the
backend sets the cookie `ikn_user` (`HttpOnly`, `SameSite=Strict`)
with the user's name. Every API request except listing and choosing
users requires it and is served for the user it names. Switching the
user shows that user's courses and tabs; their open chats stay stored.
There is no
authentication: whoever reaches the application can choose any user
(chapter 11).

==== Secrets

The Anthropic and Mistral API keys stand in plain text in `.env` (see
<<adr-operator-key>>). They are protected by:

* `.env` is never committed; the repository holds `.env.example` with
  placeholders.
* `.env` is readable only by the operator (`chmod 600`).
* The Anthropic key never leaves the AI Client, the Mistral key never
  the OCR Client: they appear in no log, error message, or API
  response.
* The operator creates each key in a workspace of its own with a
  spend limit, so a leaked key has a bounded cost and can be revoked
  on its own.

=== AI Requests

Every request type runs on one of two model tiers (see
<<adr-model-tiers>>). The configuration sets the model of each tier.

[cols="1,1", options="header"]
|===
| Request type | Tier

| Topic extraction | large
| Task assignment (exercise sheets) | large
| Task grouping | large
| Solution writing | large
| Tutoring (topic chat), including grading | small
|===

A model with adaptive thinking decides how much to think; a model
without it thinks up to a fixed budget per request.

Ingestion requests ask for their reply in a JSON schema. A request
the model declines is rerun server-side on a fallback model.

Chat requests put the context of the chat first - the topic's tasks
and reference solutions before everything else - and mark it for
prompt caching, since every message sends it again.

The AI Client logs model and token usage of every request with user,
course, and request type, the OCR Client the pages of every
conversion. The cost of an ingestion is read from this log.

Every chat request adds its input tokens, cached ones included, its
cached input tokens, its output tokens, and its approximate cost in
euros to the topic's `usage.json`. The cost is computed from
Anthropic's list prices per model and a fixed exchange rate, both in
the backend source. The UI shows these totals and their sum for the
course, and each chat reply reports its own; the
open session's total is kept in its `chat.json`.

=== Concurrency

The backend is asynchronous throughout. Every call to the Anthropic
API and every other wait on I/O is non-blocking, so one backend
process holds many streaming chats at once, beside the ingestions it
runs as background tasks - at most one per course, each tracked in
memory by the step it is at. Blocking work, such as reading and writing files, runs off the
event loop.

=== Chat Tools

The tutor acts through a fixed set of tools, offered with every chat
request and executed by the Tutor (see <<adr-chat-tools>>). No tool
reaches outside the requesting user's course. The tools' schemas are
strict and the same in every chat; the Tutor checks values that
depend on the course.

[cols="1,3", options="header"]
|===
| Tool | Effect

| `update_cheatsheet`
| Adds, changes, or removes one entry in a section of
  `cheatsheet.md`.

| `pose_task`
| Marks a task in the reply with its gradability tier; the chat shows
  the task and its tier.

| `complete_step`
| Ends a step. Takes the step - `introduction` or one of the topic's
  Tier A and B tasks; any other step is rejected with the list of
  valid ones - and a note of one sentence, empty when there is
  nothing to keep; for a Tier B task, the note is the
  student's self-rating, marked as such. Marks the introduction as
  given or the task as done, with the note, in `progress.json`, and
  computes the topic's score again. The chat continues from the updated progress without the messages
  before.
|===
