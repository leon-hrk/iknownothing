[[runtime-ingestion]]
=== Course Creation and Ingestion

[plantuml, target=runtime-ingestion, format=svg]
....
include::diagrams/runtime-ingestion.puml[]
....

. The operator puts the course's PDFs into `courses/<dir>/exams/` and
  `courses/<dir>/exercises/` next to the compose file, with
  `courses/<dir>/notes.md`, and runs `course add <user> <course>
  [<dir>]`; `<dir>` defaults to the course name. Courses refuses an
  unknown user, an existing course, and a directory that holds
  anything but `notes.md` and PDFs in `exams/` and `exercises/`, lacks
  `notes.md`, or has no PDF. It copies the files through the Course Store under
  `sources/<type>/` and as `notes.md`.
. Courses runs Ingestion in the command's process. Ingestion executes
  the steps below in order, prints each as it starts, and writes its
  results through the Course Store.
.. *Topic extraction.* One request sends all exam and exercise PDFs
   as documents together with `notes.md`
   (<<_topic_extraction,chapter 8>>) and receives the course language
   and the topics with their sources, which Ingestion checks and
   writes to `ingestion/topics.json`.
.. *Topic files.* No AI call: `topic.md` of every topic is written
   from the topics, then `topics.json`.
. The command prints the token usage. The course is ready: the
  student's course list shows it as such, and it opens.

Topic extraction applies the fallback strategies (chapter 1)
according to the number of past exams in the course.

`course add <user> <course> --from <other-user>` hands an ingested
course to a further student: Courses copies the course of the same
name from `<other-user>` through the Course Store - input and derived
files, without the student state - and makes no AI
call. A course that is not ingested is not copied.

==== Failure and Resumption

* Results are written atomically, so a result that exists is
  complete. Before issuing a request, a step checks for its result
  and skips work that is already done.
* The AI Client retries transient API errors (rate limit, overload).
* When retries are exhausted or the error is permanent (invalid API
  key, exhausted credit), the command fails with the reason. `course
  ingest <user> <course>` resumes at the first missing result.
* `topics.json` exists only for a fully ingested course; until then
  the course is listed as not ingested and does not open.

[[runtime-chat-message]]
=== Chat Message

[plantuml, target=runtime-chat-message, format=svg]
....
include::diagrams/runtime-chat-message.puml[]
....

The chat lives in the frontend. The backend keeps no chat state
between requests.

. The frontend posts the chat's scope (the course or one topic), its
  transcript so far, and the student's message.
. Tutor assembles the context for the scope through the Course Store
  (chapter 1, Tutoring Sessions) - for a topic-level chat, its source
  pages first, cut out of the PDFs - and sends it with the transcript and
  the <<_chat_tools,chat tools>> through the AI Client.
. The reply streams to the frontend as Server-Sent Events.
. When the model calls a tool, Tutor executes it and continues the
  reply with the tool result in a follow-up request. Tools with a
  visible effect emit their own event: cheatsheet changed, task
  posed.
. The frontend appends the reply and its tool calls to the
  transcript.

[[runtime-finalization]]
=== Session Finalization

[plantuml, target=runtime-finalization, format=svg]
....
include::diagrams/runtime-finalization.puml[]
....

Only topic-level chats are finalized, and only once the student has
written in them.

. A topic-level chat ends when the student opens another chat or
  chooses another user and confirms the warning, or closes the tab. The frontend posts its transcript - on tab close as
  a `keepalive` request. Tutor answers at once and finalizes in a
  background task of the backend process.
. Tutor sends one request with the transcript, the topic's
  `topic.md`, and its current `progress.md`, and receives the updated
  progress, with assessed and self-reported signals kept apart.
. Tutor writes `progress.md` through the Course Store.

Finalizations of one course run one at a time, so two sessions on the
same topic never write its progress concurrently. A finalization that
is running when the backend stops is lost.
