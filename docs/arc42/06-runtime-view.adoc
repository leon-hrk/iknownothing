=== Course Creation and Ingestion

[plantuml, target=runtime-ingestion, format=svg]
....
include::diagrams/runtime-ingestion.puml[]
....

. The operator puts the course's PDFs into `courses/<dir>/exams/` and
  `courses/<dir>/exercises/` next to the compose file, with
  `courses/<dir>/notes.md`, and runs `course add <user> <course>
  [<dir>]`; `<dir>` defaults to the course name. Courses refuses an
  unknown user, an existing course, and a directory that holds
  anything but `notes.md` and PDFs in `exams/` and `exercises/`, lacks
  `notes.md`, or has no PDF. It copies the files through the Course Store under
  `sources/<type>/` and as `notes.md`.
. Courses runs Ingestion in the command's process. Ingestion executes
  the steps below in order, prints each as it starts, and writes its
  results through the Course Store.
.. *Conversion.* Every exam and exercise PDF without a Markdown file
   goes to the OCR Client, a few at once. Ingestion writes the figures
   of each page to `sources/<type>/<file>/`, then
   `sources/<type>/<file>.md` (<<_source_conversion,chapter 8>>).
.. *Topic extraction.* For every past exam not read yet, one after
   another, one request sends its conversions without their figures,
   `notes.md`, and the topics so far (<<_topic_extraction,chapter 8>>).
   It receives the new and changed topics and the exam's sources,
   which Ingestion checks, applies, and writes to
   `ingestion/topics.json`. Each exam is printed as it starts.
.. *Task assignment.* Every exercise sheet not read yet goes in a
   request of its own, several at once, with the topics. Each reply
   assigns the sheet's tasks to the topics or to `other-tasks`;
   Ingestion checks them, applies them in unit order, and writes
   `ingestion/topics.json`.
.. *Task grouping.* One request sends the tasks of `other-tasks` and,
   in a course with past exams, those of the topics no past exam asks
   for, each with its topic, together with the topics. It receives
   new topics and the tasks that move; Ingestion checks, applies, and
   writes `ingestion/topics.json`. The step runs whenever the topics
   or these tasks differ from the last grouping.
.. *Topic files.* No AI call: the priority of every topic is computed,
   then `topic.md` of every topic is written, then `topics.json`. The
   course is ready from here on: the student's course list shows it
   as such, and it opens.
.. *Solutions.* Every topic with Tier A or B tasks whose tasks
   differ from those its reference solutions were written for - or
   that has none yet - goes in a request of its own, several at
   once, with its tasks as a topic-level chat gets them - figures
   included - its `topic.md`, and the course language. The reply
   holds a reference solution for every task whose blocks hold none;
   Ingestion checks the task labels, writes
   `topics/<topic>/solutions.md` if there is any and removes it
   otherwise, and records the topic's tasks in
   `ingestion/topics.json`.
. The command prints the token usage and the pages converted.

Topic extraction applies the fallback strategies (chapter 1)
according to the number of past exams in the course.

==== Course Update

. The operator puts further PDFs into `courses/<dir>/` - a past exam,
  an exercise sheet, or the solutions to one the course has - and
  runs `course update <user> <course> [<dir>]`. Courses checks the
  directory as for `course add` and refuses a course that is not
  ingested and a PDF whose content differs from the course's copy.
  It copies `notes.md` and every PDF the course does not have yet,
  and prints them.
. Courses runs Ingestion, which executes the steps above on what is
  new:
** A new past exam is extracted against the topics so far; its tasks
   go to existing topics or to new ones, and existing topics may
   change. A new exercise sheet is assigned.
** A unit with a document not read yet whose other documents were
   read is read again: Ingestion first removes the sources its
   earlier reading added and the topics only they made up, then
   extracts or assigns it like a new unit. Solutions added later join
   their tasks without duplicating them.
** Task grouping runs again if the topics or its tasks changed: a
   task of a topic no past exam asks for can move to a new topic of
   the exams.
** Topic files recompute every priority. Topics whose tasks changed
   get their reference solutions written again.

==== Failure and Resumption

* Results are written atomically, so a result that exists is
  complete. Before issuing a request, a step checks for its result
  and skips work that is already done.
* The AI Client retries transient API errors (rate limit, overload).
* When retries are exhausted or the error is permanent (invalid API
  key, exhausted credit), the command fails with the reason. `course
  ingest <user> <course>` resumes at the first missing result.
* `topics.json` is written once the topics are complete; until then
  the course is listed as not ingested and does not open. A course
  whose reference solutions failed opens without them for the topics
  not done; `course ingest` writes them.

[[runtime-chat-message]]
=== Chat Message

[plantuml, target=runtime-chat-message, format=svg]
....
include::diagrams/runtime-chat-message.puml[]
....

The frontend holds the transcript and sends it with every message;
the backend stores it after every reply, so an open chat survives a
reload. Opening a chat loads its stored transcript.

. The frontend posts the chat's scope (the course or one topic), its
  transcript so far, and the student's message.
. Tutor assembles the context for the scope through the Course Store
  (chapter 1, Tutoring Sessions) - for a topic-level chat, its tasks
  first (<<_topic_extraction,chapter 8>>) - and sends it with the transcript and
  the <<_chat_tools,chat tools>> through the AI Client. Of a
  topic-level transcript, only the messages since the last completed
  step are sent.
. The reply streams to the frontend as Server-Sent Events: the
  summary of the model's thinking, the text, and the start of each
  tool call. Until the text arrives, the frontend shows the thinking
  summary and what the model is doing (thinking, or the tool it
  calls); afterwards the thinking stays in the chat, collapsed.
. When the model calls a tool, Tutor executes it and continues the
  reply with the tool result in a follow-up request. Tools with a
  visible effect emit their own event: cheatsheet changed, task
  posed, step completed.
. When the model completes a step, Tutor marks the introduction as
  given or the task as done, with the model's note, in the topic's
  `progress.json`. It assembles the context again with the updated
  progress and sends the follow-up request without the step's
  messages.
. Tutor stores the transcript with the reply and the session's token
  usage in the scope's `chat.json`.
. The frontend appends the reply and its tool calls to the
  transcript.

A session ends when the student chooses *End session* and confirms.
The frontend asks the backend to end the scope's chat, and Tutor
removes its `chat.json`. The progress recorded in its steps stays.
