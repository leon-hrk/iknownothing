== Introduction and Goals

iknownothing is a self-hosted, AI-powered exam preparation tutor. The
student uploads their course materials and says "I know nothing" -
the agent builds a structured, topic-based study plan and tutors them
through it, from knowing nothing to exam ready. Along the way it keeps
a cheatsheet of what the student has learned and tracks their progress
per topic.

=== Requirements Overview

==== Problem

Students preparing for exams have scattered materials: lecture slides,
exercise sheets, past exams. Generic AI chats don't know the
professor's style, the exam's difficulty level, or what the student
already knows. Every chat starts from zero, and what the student
worked out in one is gone in the next.

==== Core Idea

The agent ingests all course materials *once*, distills them into
structured, reusable Markdown artifacts (topics, example problems,
solution styles), and uses these artifacts as context for tutoring
sessions.

What the student learns is kept in two living artifacts: a
*cheatsheet* of key terms, formulas, and strategies, which the tutor
fills during chats, and a *progress* file per topic, updated after
every session on that topic. Every new session starts from them
instead of from zero.

==== Accounts and Hosting

* Self-hosted web application for small deployments.
* Multi-user: per-user courses and progress. No data is shared
  between users.
* The operator creates the accounts; users log in with name and
  password. There is no self-registration.
* The operator provides one Anthropic API key for the instance. All AI
  calls of all users, including ingestion, run on that key.

==== Course

The top-level unit, owned by a user. A course contains:

* *Lecture material* (PDF) - slide decks, usually one per lecture, or
  a lecture script
* *Exercise sheets + solutions* (PDF)
* *Past exams + solution proposals* (PDF)
* *Notes file* (`notes.md`, required) - free-form remarks the AI must
  respect (e.g. "prof emphasized topic X in Q&A", "topic Y is new
  this year")

[[ingestion-pipeline]]
==== Ingestion Pipeline

Runs per course. Ingestion builds the topics in *passes* over the
uploaded PDFs; the material is not converted to Markdown as a whole.
Every pass reads a part of the material together with `notes.md` and
the topics built so far, and returns only what changes.

. *Exam passes*: the past exams and their solution proposals. They
  create the topics, ranked by how often and how prominently the
  exams ask for them, and fill each with what the exams show about
  it. What the exam asks defines what a topic _is_. Through
  `notes.md`, a topic no past exam covers ("topic Y is new this
  year") is still created. The course language is detected here.
. *Exercise passes*: the exercise sheets and their solutions. They
  fill gaps in the existing topics and add topics the exercises cover
  and the exams do not. Source priority: *past exams > exercises*.
. *Lecture passes*: the lecture material, read against the *open
  points* of all topics - what the tutor needs to teach a topic that
  exams and exercises do not contain: definitions, formulas,
  derivations, notation. Every passage that answers an open point is
  transcribed as an *excerpt* with its file and pages. Nothing else of
  the lecture is transcribed, and the lecture creates no topics.
  Without lecture material, these passes are skipped.
. *Topic files*: every topic gets a *topic directory* with its
  artifact, `topics/<topic>/topic.md`:
** Topic description and exam relevance (priority)
** The task types the past exams ask on the topic: kind, length,
   difficulty, and how often they appear
** Two or three original exam tasks with their solutions as example
   problems, each with its <<gradability,gradability tier>>,
   difficulty, and expected working time. With few or no past exams
   on the topic, the example problems come from the exercises, and
   difficulty and working time are estimates marked as such.
** Solution approaches "the professor's way"
** The lecture excerpts
** Out-of-reach task types, if any
** Open points the course material does not answer. The tutor marks
   what it explains on them in its own words.
. *Topic list*: `topics.json` - the topics in priority order, each
  with its priority and its topic directory. The UI orders the topic
  tree by it; the course-level chat takes the priorities from it.

What ingestion transcribes from the PDFs - example problems and
excerpts - follows the same rules:

* Math is written as LaTeX.
* *Figures and diagrams* are converted to text. Where the content
  has a meaningful text form (block diagrams, state machines, flow
  charts, tables, trees), it is reproduced as ASCII art; otherwise it
  is replaced by a textual description. No image files are extracted.

For solution style and notation the source priority *inverts*:
lecture material, exercise solutions, and past exam solutions - in
this order - outrank the exam question itself. The exam says what is
asked; the lecture says how it is to be written down.

Tutoring runs on the topic directories only; it never reads the
original PDFs.

==== Course Lifecycle

A course is ingested *once*, from the PDFs and the `notes.md` uploaded
when it is created. Ingestion does not start without `notes.md`.
Nothing can be added to or changed in a course afterwards.

The student can read every Markdown file of a course but edits none.
Only the tutor writes after ingestion: `cheatsheet.md` through the
chat, `progress.md` on finalization.

==== Fallback Strategies

The pipeline adapts to the material the student can provide:

* *Many past exams*: extract topics and difficulty directly from
  exams.
* *Few past exams*: use exercise problems as the base, calibrate
  difficulty against the few available exam problems.
* *No past exams*: use exercise sheets only; filter out extremely
  hard exercises and normalize difficulty to a realistic exam level.

[[gradability]]
==== Task Gradability

Not every exam task can be posed and corrected in a chat window.
Every example problem is classified during ingestion into one of
three tiers, and the tier determines how the tutor handles it.

*Tier A - graded.* Text, math, derivations, code, short answers. The
normal loop: tutor poses the problem, student answers, tutor grades
and gives feedback. Result feeds `progress.md` as an *assessed*
mastery signal.

*Tier B - posed, self-assessed.* Tasks whose solution can be
expressed in ASCII/Markdown: state machines, flow charts, simple
block diagrams, truth tables, tree structures, timing diagrams. The
tutor poses the task and can show a reference solution in ASCII, but
does *not* grade the student's attempt. Instead the student
self-reports ("got it" / "struggled" / "no idea"). Result feeds
`progress.md` as a *self-reported* signal, explicitly marked as such.

*Tier C - out of reach.* Tasks with no meaningful text
representation: freehand sketches, hand-drawn plots, circuit layouts,
geometric constructions, anything graded on visual precision. These
are *not posed as exercises*. They are listed explicitly in the topic
artifact and surfaced to the student: "This topic's exam typically
includes <task type>. This tutor cannot train that - practice it on
paper."

The tier is a property of the _task_, not the topic - a topic usually
contains tasks from more than one tier.

==== Tutoring Sessions

Sessions come in two scopes.

*Course-level chat* - orientation and planning. This is the default
entry point: the student opens a course and asks "which topics do I
still need to learn?". Context is `notes.md`, the progress of every
topic, the topic priorities from `topics.json`, and `cheatsheet.md` -
never a full topic artifact. It answers where the student stands and what
to work on next; to work on a topic, the student opens it.

*Topic-level chat* - the actual tutoring, opened by clicking a topic.

Exactly one chat is open at a time. Clicking a topic or the course
opens a new chat and ends the current one; closing the browser tab
ends it too. Since chats are not stored, the student confirms before
a chat with messages in it is ended by opening another one.

* Context loaded into a topic-level session:
** The topic's artifact (`topics/<topic>/topic.md`)
** The course cheatsheet (`cheatsheet.md`)
** The topic's progress (`topics/<topic>/progress.md`)
** The course notes (`notes.md`)
* A topic directory is also directly readable: the student can open
  its files without starting a chat.
* The tutor adapts: "I know nothing about this" - guided
  introduction; "quiz me" - exam-style problems with feedback, at the
  difficulty and working time the topic artifact gives.
* Tier B tasks are offered alongside Tier A ones, but the UI switches
  from "submit answer" to "show solution, then rate yourself".
* If the topic has Tier C tasks, the session mentions them once, so
  the student knows what they still have to practise elsewhere.
* Solutions always follow the professor's conventions and notation.
* *Language*: the tutor responds in the language of the course
  materials, detected during ingestion - the language the exam is
  written in. It is not configurable.
* *Chats are not stored.* A chat exists in the browser while it is
  open. What lasts from it is written to `progress.md` and
  `cheatsheet.md`.

==== Living Artifacts

* *`cheatsheet.md`* - key terms, formulas, and solution strategies
  the student has encountered. The tutor updates it during chats, as
  soon as something worth keeping comes up, so the student can use it
  while solving tasks. The student changes it by asking the tutor in
  the chat.
* *`progress.md`* - one per topic: what the student can do, where
  they struggle, what to review next. Assessed signals
  (Tier A) and self-reported ones (Tier B) are kept distinct - a
  student's self-rating is useful but is not evidence, and the tutor
  does not treat it as such.
* *Finalization*: whenever a topic-level chat ends, the topic's
  `progress.md` is updated from the chat. Every new session starts
  informed about the student's current level.

==== User Interface

A classic AI chat app: a collapsible course tree on the left, one
large chat on the right. The student never has to learn a special
interface - they open a course and ask a question.

....
+-----------------------------+------------------------------------------+
| iknownothing            [+] | Control Theory                           |
+-----------------------------+------------------------------------------+
|                             |                                          |
| v Control Theory            |                    +-------------------+ |
|   v Topics                  |                    | Which topics do I | |
|   |  > Laplace              |                    | still need to     | |
|   |  > Stability            |                    | learn?            | |
|   |  v Observers            |                    +-------------------+ |
|   |      topic.md           |                                          |
|   |      progress.md        | Three topics are still open, in exam     |
|   |  > State Space          | priority order:                          |
|   |  Notes                  |                                          |
|   |  Cheatsheet             | 1. Observers - high priority, never      |
| > Signals & Systems         |    practised                             |
| > Thermodynamics            | 2. State Space - high priority, never    |
|                             |    practised                             |
|                             | 3. Stability - Nyquist is where you      |
|                             |    keep slipping                         |
|                             |                                          |
|                             | I'd start with Observers.                |
|                             |                                          |
|                             | +------------------------------------+   |
|                             | | Ask anything...                 >  |   |
|                             | +------------------------------------+   |
|                             |                                          |
+-----------------------------+------------------------------------------+
....

* *Courses* are the top level. Clicking one opens a new course-level
  chat and reveals everything that belongs to it.
* *Topics* are sorted by exam priority. Clicking one opens a new
  topic chat; expanding it lists the files of its topic directory.
* Clicking the course or a topic while a chat with messages is open
  first shows a warning that the current chat will be lost; the new
  chat opens only once the student confirms.
* The *main area* is an ordinary chat. Planning, tutoring, and
  quizzing all happen there.
* Clicking a Markdown file turns the main area into a Markdown reader
  that shows the file rendered and read-only: the files of a topic,
  *Notes*, and *Cheatsheet*. The open chat is not ended by this; the
  student switches back to it.
* Uploaded PDFs are not shown.

==== Out of Scope

Direction, not a plan. Nothing here is designed.

* *Hosted version.* A managed deployment reachable over the web, so a
  user does not have to run Docker at all. Hosted users choose
  between their own API key and an all-inclusive plan billed through
  the service.
* *Retrieval and AI tooling.* RAG, vector search, and agentic tool
  use beyond the fixed chat tools, evaluated against the
  structured-artifact approach.
* *Topic review.* The student confirms, renames, merges, adds, or
  removes the topics before the topic files are written.
* *Course dashboard.* A per-course overview with mastery per topic, a
  readiness estimate that names the Tier C share separately, and
  recommended next steps.
* *Mock exams.* The tutor poses a full exam in the shape of the
  real one.
* *Chat history.* Storing chats so the student can revisit them.
* *Editing in the UI.* The student edits `notes.md` and
  `cheatsheet.md` directly; afterwards the AI reworks the edited file
  so it is consistent again.
* *Course updates.* Adding material to an existing course, editing
  derived files, and incremental re-ingestion that rebuilds only what
  a change affects while keeping student progress and user edits.
* *PDF viewer.* The uploaded PDFs shown in the UI.
* *Figure extraction.* Figures and diagrams extracted from the PDFs
  as image files and shown in the UI next to their text form.
* *EU-hosted AI providers*, for users who cannot or will not send
  course material to a US provider.
* *Sharing course material between accounts.*
* *Per-user API keys.* Every user enters their own Anthropic API key
  in account settings, and their AI calls run on it.
* *Self-service accounts.* Self-registration, and users changing their
  own password.

=== Quality Goals

Ordered by priority. Concrete scenarios are in
<<_quality_requirements,chapter 10>>.

[cols="1,1,3", options="header"]
|===
| # | Quality goal | Meaning

| 1
| Exam readiness
| Ingestion captures every topic the exams ask for and prepares its
  material. The tutor guides the student through the topics up to the
  exam's level, not beyond, and keeps progress and cheatsheet along
  the way.

| 2
| Cost efficiency
| Material is ingested once, sessions load only the current topic's
  context, and every request type runs on the model tier that fits
  its task.

| 3
| Transparency
| Every Markdown file of a course - topic artifacts, notes, and
  student state - can be opened in the UI and is shown rendered.

| 4
| Honesty
| The tutor states what it cannot train and names the task types the
  student has to practise elsewhere. Self-reported signals are never presented as assessed ones.

| 5
| Tenant isolation
| All data is strictly namespaced per user. No state is shared
  between users.

| 6
| Ease of self-hosting
| One `docker compose up`. No GPU, no model weights in the image.
|===

=== Stakeholders

[cols="1,3", options="header"]
|===
| Role | Expectations

| Student
| Gets from scattered course material to exam readiness with a tutor
  that knows the course, its exam style, and their current level.
  Keeps control over their data.

| Operator
| Runs an instance for themselves or a small group with minimal
  setup and no special hardware. Provides the Anthropic API key, pays
  for all AI calls, and manages the accounts.

| Developer
| Builds against this specification; needs clear boundaries and
  current, non-contradictory documentation.
|===
